# 无极军团 Codex 2.1 完整升级方案

> 本文是从无极军团 2.0 原地升级到 Codex 2.1 的唯一规范。它完整承接已确认的 3.0 理念，但只规定能够在当前 Codex 宿主可靠实现的部分；不要求阅读其他架构文档才能实施。本文中的“已实现”必须由真实代码、命令和测试结果证明，设计文字本身不构成完成证据。

## 1. 定位、目标与非目标

Codex 2.1 是 2.0 的渐进升级，不是 Pi 3.0 的重写，也不是第二套工作流。它要把当前系统从“能力包 + 路由”升级为：

```text
Luna 阿极的需求状态
→ Sol 参谋本部的任务图与调度状态
→ 最小上下文的有界子代理
→ 可验证产物与验收
→ 可追溯的失败经验和能力谱系
```

2.1 的目标：降低无关上下文、阻止无限失败循环、保留用户意图与执行证据、让外部能力能够被拒绝或融合为可调用的新物种，并在不常驻多模型的前提下按需获得官员视角。

2.1 不做以下事情：

- 不创建 Nuwa、第二阿极、第二路由器、平行 v2 页面或默认官员议会。
- 不把完整聊天、完整 Skill 正文、完整父任务或秘密当作活跃上下文。
- 不伪造 Codex 不具备的宿主能力：不能由 Skill 从当前主线程物理删除历史消息。
- 不自动扫描、下载或安装外部来源；不因用户提交项目就强行融合。
- 不把 `callable`、mount 或 smoke 等同于“已融合”“behavior-verified”或 `primary`。

所有持久资料、规范文档、能力来源和实施产物优先保存于 `E:\wuji-projects\wuji-legion-codex-2.0`；不得只在 C 盘留下唯一副本。

## 2. 组织、职责与模型

### 2.1 阿极与参谋本部

- **Luna 阿极**是唯一用户接口：多轮澄清、维护需求/决策状态、向用户汇报；不合并执行结果、不制作制品，也不判定完成。
- **Sol 参谋本部**只从阿极交付的需求快照开始：维护任务图、选择执行节点模型、投影最小上下文、跟进回执、局部重规划与需求复核。实际派发由宿主完成；它不得改写用户需求、执行任务、写制品或验收完成。
- 两者不是竞争路由：阿极处理需求对话单元，参谋本部处理已形成的执行节点。

### 2.2 子代理模型

| 模型 | 适用任务 |
|---|---|
| Luna | 不依赖父上下文的机械提取、明确检索、格式转换、重复验证 |
| Terra | 普通实现、理解、判断和多数工程任务 |
| Sol | 有边界的架构、复杂推理、困难根因和高要求审查 |

模型选择只在参谋本部形成具体执行节点后发生；用户最初一句话的表面难度不能决定模型。一个子代理只使用一次确定的模型和 `session_key`，不自动切换、不假设跨模型缓存共享、不因质量自动付费重试。只有宿主返回真实 agent ID、模型、输入工件和结果句柄，才算发生子代理执行。

## 3. 需求、决策与对话证据图

### 3.1 需求图

需求图回答“用户真正要什么”，不是实现方案。它是可增删拆合的分层表，而非固定表单。每个需求单元必须具有：

```text
unit_id / revision_id
目标、想要、不要、约束、偏好、优先级、验收
未决问题、冲突、依赖与影响关系
来源消息 ID、变更链、状态与证据句柄
```

“不要什么”优先记录在具体受影响单元；只有身份、安全和全局硬边界进入精简的全局约束区。

### 3.2 决策图与对话证据

决策图是用户采纳、拒绝、暂缓或修改的不可变事件账本；需求图是这些决定生效后的当前投影。两者不能各自改写“用户真实意图”。

原始聊天是冷证据，不是长期活跃记忆。每次修改记录消息 ID 与前后修订；只有摘要冲突、用户要求或证据不足时，才按单元回读局部消息。聊天、摘要、错误输出和证据在入库前必须脱敏，禁止存储密钥、密码或完整敏感提示。

### 3.3 稀疏投影与 Codex 限制

阿极每轮使用：

```text
动态空表骨架
+ 当前活跃单元
+ 必要依赖片段
+ 尚未写入图谱的最小对话状态
+ ID / 版本 / 来源指针
+ 当前用户消息
```

用户切换单元即切换投影；整体总结或进入执行时才生成结构化总快照。Codex 2.1 可把这种投影交给新子代理/执行会话，实质降低干活分支的上下文；主聊天窗口的历史由宿主控制，Skill 无法物理清空。

未来 Pi 3.0 的目标是同一 UI 保留完整聊天、而每次模型调用从图谱最小投影重新开始。2.1 只记录这个目标，不把近似实现称为原生同窗重置。

## 4. 执行图、子代理与验收

参谋本部从版本化需求快照建立独立执行图。每个执行节点包含：

```text
task_id / revision
引用的需求单元和精确修订
目标与排除项、输入/输出句柄、依赖、模型理由
最小上下文投影、预算、联网/写入/分支边界
验收条件、验证方法、证据、状态、失败与恢复记录
```

子代理只获得本节点所需的任务契约、局部需求、接口、输入、输出、验收与失败回报；不继承完整父聊天，也不拥有长期全局图。机械任务只拿操作和格式，普通任务附加相关约束，高推理任务才读取必要需求子树或架构边界。

最终验收必须对账：

```text
有效需求修订 → 执行任务 → 产物 → 验证方法 → 验证证据 → 验收结果
```

执行节点完成数不能代替交付。需求变化只使精确引用该修订及其下游的节点失效；无关、已验收的节点和证据保留。

## 5. 任务熔断与失败经验

系统以确定性的任务尝试账本阻止无限循环。尝试指纹至少包括：

```text
任务节点、操作意图、规范化命令/工具调用、输入版本、环境、策略 ID、错误指纹
```

规则为：

1. 完全相同的尝试只在有瞬态故障证据时允许额外重试一次；确定性错误不得盲重试。
2. 同一策略连续两次失败，必须换实质不同的方法；改命令写法、提示词措辞或重启同流程不算新策略。
3. 三种策略或五次无进展失败后停止该节点并报告，不得自动开启新一轮循环。

新的可信证据、有效产物、关键输入/环境变化、有效图谱修订或有意义的错误变化才算进展。熔断后可查询匹配的全局经验、做有边界研究、升级模型、请求用户决定或明确阻塞；不能无止境消耗 Token。

全局经验图只在失败、能力缺口或明确复用时查询。它记录范围、根因、恢复、验证、TTL、失效条件与替代关系，不保存完整日志、聊天或秘密；第一次失败只是候选，经过验证或重复成功才成为可复用经验。

## 6. 完整图谱体系在 2.1 的边界

2.1 不把所有内容做成万能图，而是采用职责分离和最小引用：

| 图谱 | 所有者 | 2.1 职责 |
|---|---|---|
| 需求、决策、对话证据 | 阿极 | 用户意图、决定与局部溯源 |
| 执行、验收、尝试账本 | 参谋本部/确定性执行器 | 执行状态、证据与熔断 |
| 工作区代码图 | 工程能力 | 文件、符号、测试、依赖和影响范围；可重建 |
| 研究证据图 | 研究能力 | 有范围的来源、声明、反证与过期时间 |
| 事件根因图与全局经验图 | 根因能力/进化主帅 | 候选根因、验证恢复和跨项目复用 |
| 能力谱系融合图 | 进化主帅 | 来源、版本、物种、资产、适配器、拒绝与更新 |
| 性能证据图 | 性能能力 | 可见的延迟、成本、成功率、质量与回退证据 |
| 安全信任、合规义务图 | 安全/合规能力 | 权限、数据流、许可证、义务和处置；不存秘密 |
| 官员观点图 | 独立官员 | 按次、只读、建议性质的观点与证据 |

跨图只用稳定 ID、版本、证据句柄和受限关系引用；任何图都不能跨权修改其他图的正式事实。模型只是变更提议者，真正写入必须经过 schema、授权、幂等、版本事务和追加式审计。

## 7. 官员 MoE 与保卫科

### 7.1 官员

白帽等单项官员默认休眠；简单任务由 staff 做证据复核，中型任务只做内部质检，大型/高风险任务默认启动一次 composite MoE 独立官员质检，治理风险在同次审查增加审计分节。每个职权有低成本触发契约，由任务类型、阶段、产物类型、错误/性能信号、证据缺口或风险标记触发：

```text
当前任务/产物/事件
→ 确定性信号
→ 仅选择相关职权
→ 主模型局部检查
→ 必要时才启动一个真实独立实例
→ 建议与证据回执
→ 用户决定是否采纳
```

官员不能互调、不能形成默认委员会、不能改写需求/执行图或替代用户。白帽只服务用户，在讨论和方案选择阶段提出反例与备选；用户确认后退出热路径。真实独立审查必须有独立任务、最小投影和可追溯回执，内部反方检查不能冒充白帽执行。

### 7.2 事件触发保卫科

保卫科模型默认休眠，不轮询、不保留上下文、不消耗 Token。只有联网、外部下载、Skill/MCP/代码引入、命令执行、文件写入、账号/密钥、权限提升、发布、付款或删除等受控动作发生前，才运行一次极小的确定性门禁。

门禁可以允许、要求确认、最小权限限制或阻断；没有受控动作即没有保卫科工作。只有规则无法判定或用户要求独立安全意见时，才通过 MoE 启动保卫科模型。安全硬边界不等待模型讨论；安全建议仍由用户取舍。

## 8. 进化主帅：创造新物种

进化主帅不是项目收藏器、Skill 比武裁判或规则拼接器。它接到用户提交的外部项目后，先决定是否适合无极军团；用户的“是否有帮助”是评估请求，不是融合命令。

### 8.1 结论与最小记录

结论只能是 `融合提案`、`仅借鉴`、`拒绝` 或 `待证`。拒绝、未采用或仅借鉴的项目不保留完整快照、模板、组件、脚本或冷存候选，只保留：

```text
source_id、source_version_id、分析时间、结论、理由、少量证据句柄、重新分析条件
```

同一版本再次提交时直接提示既有结论；只有用户重提、再次要求融合或主动要求检查时才分析新版本差异。2.1 不后台扫描、定时抓取或自动下载上游更新。

### 8.2 规则、资产与调用链

融合是创造新规则，而不是让父代 Skill 轮流调用。项目的策略、基本操作、适用条件、边界、脚本、配置与质量机制先被对齐；重复被删除，互补部分生成新的决策结构。运行时调用的是融合物种的新规则，不是把父代提示并排塞进上下文。

模板、组件、素材、脚本和配置同样是能力。它们可以累加：例如 10 个红色模板与 10 个蓝色模板可完整继承为 20 个模板，而不是互相淘汰或压成通用模板。但每个计入成果的资产都必须具有：

```text
asset_id → 来源与版本 → 依赖/兼容条件 → 可检索目录
→ 融合规则的选择条件 → 统一入口的真实加载、渲染或执行
```

组件不必强行兼容每一个模板；兼容关系必须显式记录。不能从融合 Skill 的统一入口真实定位、选择和调用的资产不算融合成果，也不作为“以后可能有用”的库存。

### 8.3 谱系、版本与用户确认

每个已采用能力记录：

```text
source_id / source_version_id / atom_revision_id
fusion_species_id / fusion_revision_id / release_id
```

规则必须说明删除了什么重复、继承了什么互补、增加了何种父代没有的新决策；资产必须说明调用链。上游更新时沿谱系定位受影响原子与物种，提出新一代而不覆盖旧代。来源材料只有在用户确认融合提案后才进入物种。

对外部 Skill、Plugin、MCP 的优先顺序为：用户明确选择 → 精确匹配的已安装官方能力 → 行为验证的策展能力 → 更优的行为验证 Wuji 能力 → 原生工具/已有依赖 → 有界外部研究 → 最小新实现。官方身份、README、星标或可安装性都不是融合证据。

## 9. 数据、权限、上下文与成本

- 稳定前缀保持小；日志、全文聊天、完整图、完整 Skill 正文和大资产保持冷态。
- 每次跨图读取必须声明目的、路径、最大跳数、分支、对象数、字节与时间预算；默认拒绝跨项目读取。
- 谱系索引不等于权限系统：ID 不可枚举，每次解析仍做项目命名空间与 ACL 检查。
- 所有数据入库前脱敏；秘密仅保留不透明 vault 引用，敏感内容不得使用可猜测明文哈希。
- 记录延迟、失败、重试、上下文大小、Token/费用（仅当宿主可见）和返工率；不可见遥测必须标记未知。
- 进化和经验默认不自动注入普通任务；只有精确匹配事件才查询。

## 10. 实施顺序与模型建议

2.1 按小切片实现；每个切片完成真实测试、变更审计与文档状态更新后才进入下一个。

| 切片 | 内容 | 推荐模型 |
|---|---|---|
| 0 | 盘点现有代码、Git 状态、测试和 E 盘文档；修复基线 | Terra high |
| 1 | 任务尝试账本、策略/无进展熔断与定向测试 | Terra high |
| 2 | 需求/决策图、执行/验收映射、稀疏投影与子代理契约 | Terra xhigh |
| 3 | 事件触发安全门禁、MoE 官员选择契约 | Terra high；必要时 Sol xhigh 审查 |
| 4 | 能力谱系、融合基因组、资产调用与可达性验证 | Terra xhigh；Luna 用于机械盘点 |
| 5 | 真实回归、性能/上下文测量、文档与退役旧路径 | Terra high |

在每个切片开始前，应明确下一步、模型、推理强度、目的、范围和停止/验收条件；但除外部凭据、不可逆动作或真正产品决策外，不要求用户逐步说“继续”。

## 11. 验收与完成声明

任何实现完成声明至少提供：实际命令、修改文件、测试输出、产物/证据句柄、Git 状态、已完成项、未完成项和真实阻塞。不得用路由 JSON、安装成功、代码编译、模型自报、文档存在或单个 smoke 代替验收。

最低行为验收：

1. 长对话修改一个需求单元时，只投影该单元和必要依赖。
2. 需求、决策、执行和验收可通过稳定 ID 与版本溯源，用户修改只局部失效。
3. 子代理不能获得全文父上下文、改写需求或宣布全局完成。
4. 重复尝试、重复策略和无进展任务都在阈值处确定性停止。
5. 保卫科不常驻模型；受控动作才产生门禁，歧义才建议独立审查。
6. 官员只按触发契约提出建议，用户采纳后才写入正式图谱。
7. 融合物种能定位并调用其声明继承的规则/资产；不可调用资产不会被列为融合成果。
8. 同一来源版本不会被重复分析；新版本只检查谱系相关差异。
9. `gofmt`、相关定向测试、`go test ./...`、`git diff --check` 和 Git 状态审计全部真实执行；失败项必须如实保留。

## 12. 当前实施状态的纪律

仓库中可能存在尚未验收的 2.1 代码改动、生成工件或架构草稿。它们只能被标记为“待核验”，直到有人在实际工作区执行测试、检查差异、确认无第二路由/越权写入/敏感数据泄露，并将结果写入本节的实施记录。未经过这一过程，不得称 2.1 第一阶段已完成。
