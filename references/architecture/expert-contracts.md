# 专家契约与 MoE 路由

无极军团采用“静默专家、按需唤醒”的 MoE 结构。专家不是常驻模型，也不是第二个用户入口，而是**参谋部执行图中的任务级执行契约**。目录见 `capabilities/experts/manifest.json`。

## 在无极军团主链中的位置

专家不是阿极的替代品，也不是独立路由器。当前主路由的顺序是：

```text
用户自然语言
  -> 阿极收集并维护需求表/需求图
  -> 阿极应用 PonyTail 最小正确原则和白帽判断
  -> 阿极把自然语言转成结构化任务语义（目标、风格、约束、验收）
  -> 形成版本化需求快照
  -> 小任务由阿极直接完成；复杂任务才由参谋部建立任务图、确定依赖并派发
  -> 选中的师团主帅本身就是该领域专家团，负责目标、边界、组合和验收
  -> 专家团从自身专家中选择最小专业执行单元
  -> 唯一命中的领域专家将编译规则、工作流、验收步骤写入受哈希保护的 worker 契约
  -> 受限执行节点完成任务
  -> 独立验证与回执
  -> 阿极对账并向用户汇报
```

豆包工作、WorkBuddy 的可借鉴点是“预置高质量领域流程，用户无需手选专家”。在无极军团中，这些预置专家只能作为参谋部任务节点的冷能力包；阿极仍负责需求理解、质疑和最终沟通，参谋部仍负责确定性派发，专家不得自行收集需求、修改需求表、派发其他专家或宣布完成。

## PonyTail 的全角色约束

PonyTail 是全链路的共同执行原则，不是阿极的人格标签。阿极、参谋部的任务分析、专家的专业思考与提示词编译、执行节点的制品生成、验证节点和最终汇报都必须遵守：

- 用最少的上下文和 token 表达足够完成任务的信息；
- 能直接回答就不规划；能少思考就不大量思考，一行正确解决就不写多行；
- 先复用现有能力、模板、依赖和工具，再新增代码或流程；
- 选择最小正确路径，避免无关分支、重复解释和无边界重试；
- 证据不足时指出不确定性，不用更长文本掩盖缺口；
- 以真实执行和验证证据为完成依据。
- 不因节省步骤而省略事实核查、安全边界、用户约束或必要验证。

## 需求语义与专业提示词

阿极不应替专家临时编写所有领域细节。它先把用户话语抽取为结构化需求语义，例如“生成美女画像”至少包含主体、外观/风格偏好、构图、用途、输出尺寸、质量要求、禁用项和验收标准。随后由图像专家的固定流程把这些字段编译为绘画模型可执行的提示词、负面提示词、参数和生成/检查步骤（如适合时加入 4K、光影、镜头和材质描述）。

因此职责边界是：阿极负责忠实理解与澄清，参谋部负责把已确认语义编成任务节点，领域专家负责专业化提示词和工具流程；任何一层都不能凭空添加违背用户意图的风格或要求。

## 生命周期

```text
自然语言 -> 阿极识别场景 -> 复杂任务进入参谋部 -> 选中 capability 主帅及其冷专家团
          -> 词面唯一匹配才绑定一个专家；并列/无匹配交回阿极复核
          -> 仅挂载已验证且预算内的来源，生成有界任务契约
          -> 执行节点 -> 独立验证 -> 反馈账本
```

没有命中、证据不足或白帽判断认为不合理时，专家保持缄默，阿极复核后澄清、拒绝或走最小通用路径。预算不足或目录损坏时禁止专家委派，不把失败伪装成普通执行。专家不得自行唤醒其他专家、扩大权限、修改路由规则、接管需求表或宣布完成。

运行态严格分开：目录和团队完整 SOP 是冷态；唯一选中并成功绑定 worker 后才构造本任务的专家执行契约；路由 `planned` 不是 `active`/`complete`。无匹配、并列或绑定失败只保留有限诊断，不热注入其他专家的人设与阶段表。任务成功、失败或取消后释放任务级上下文；长期只保留必要的来源谱系、哈希、验收/失败证据，不保留常驻专家人格。当前 Go 路由是无会话内存的契约准备器，无法控制 Codex 宿主原生子代理退出；没有真实宿主回执就不得宣称“用完即退”已经端到端验证。

## 全角色任务图与并发

阿极、参谋部、师团主帅/专家团、专家、官员、验证角色和 worker 都拥有各自的短寿命任务图。每张图使用同一 `RoleTaskGraph` 契约，独立 ID、版本和哈希，包含依赖、验收、状态、压缩上下文句柄、`sparse-role-moe` 标记与 PonyTail 原则。子图通过父图 ID 和内容寻址句柄继承最小必要上下文，不复制完整聊天记录；完成状态只由可信宿主执行回执与适当验证推动。

任何角色都可按需拆成多个子代理。默认不拆；仅当子任务彼此独立、并发有实际收益、上下文自包含且没有共享写冲突时并发。依赖节点分批串行，失败只阻断下游，写入相同目标的节点不得同组运行。复合请求可建立多个师团主帅图（例如文章与配图），但有产物依赖的流程必须按依赖排序。

## 专家与专家团模板

每个师团主帅就是该领域专家团本体，负责领域任务图、按需唤醒和并发编排、验收与升级；不得额外套第二层专家团。专家清单采用固定模板，源于项目留存的专家/专家团模板和第五、六周素材书写思路；每项都必须落到可执行的范围或证据，不能只写人设：

| 字段 | 作用 |
| --- | --- |
| `role_type`、`decision_mode` | 明确专业角色及稀疏 MoE 的有限决策方式 |
| `mission`、`capabilities`、`commander` | 明确目标、领域和唯一所属专家团 |
| `inputs`、`constraints` | 明确任务所需输入、用户约束和不可推断项 |
| `tool_policy`、`source_ids`、`skill_sources` | 限定可用工具/已准入来源；声明不等于来源已接通 |
| `prompt_compiler`、`workflow`、`methods` | 把已确认意图编译成最短专业步骤；按本次请求最多注入两条匹配方法 |
| `outputs`、`acceptance`、`verify` | 定义交付物、验收条件与核验办法 |
| `boundaries`、`escalation`、`anti_triggers`、`failure_states` | 规定拒绝误触发、停止、回交和失败状态 |
| `ponytail_rules`、`white_hat_checks` | 贯彻最小正确原则，同时保留必要的事实、安全、授权与完成证据检查 |
| `promotion_evidence` | 规定专家何时可凭独立探针和来源证据升级；不允许自我晋级 |

运行时强制校验以上字段；选中专家时，把该专家的输入、输出、工作流、约束、工具策略、验收和白帽/PonyTail 检查编译进带目录哈希的 worker contract，仅按请求注入匹配方法。完整模板留在冷目录，避免把所有专家资料塞进每个请求。契约超过 4096 字节或总重放超过 9216 字节时仍拒绝委派，不通过删掉安全和验收字段来挤预算。总重放上限由 8192 调整至 9216，是因为真实模板字段与已验证来源同时注入后，基础 PPT 路由实测约 8645 字节；单项契约与共享上下文上限未变。工具策略目前是合同约束，不等同于宿主级沙箱/白名单；只有真实宿主执行器落实后才能声称强制隔离。

若专家需要专属 Skill，把来源先按能力准入流程登记在所属 capability 的 `sources`，作为冷、可调用的 `optional` 入口，再在专家目录以 `source_ids` 引用。只有该领域的唯一命中专家才装载它；来源、目录和 worker 任务都须通过各自哈希/字节门禁。新增来源不自动使专家成为已行为验证的宿主代理。

## 进化

专家升级只接受真实失败、复用、来源和验证事件。新流程先作为候选版本运行对照测试；只有独立验证文件、SHA-256、边界复核和内容寻址 promotion receipt 齐全，才允许替换当前版本。失败候选保持可追溯但不自动进入路由。

具体准入、现有能力继承和冷→任务热→退出的同一套规则见 `references/expert-templates/evolution-admission.md`。
