# 1、PiDeck 无极军团定制方案

本文将“无极军团 3.0”定义为 PiDeck 上的目标运行方式，而非替换 Pi 或另起一套聊天宿主。PiDeck 继续提供桌面 UI、RPC 通道、模型与会话树；无极军团以全局 TypeScript 扩展、每项目受控状态目录、可选隔离子进程和桌面控制台组成。近期交付以 Codex 2.1 的渐进原则为准：先建立可验证的需求、决策、执行与安全边界，再增加官员、能力谱系和子代理。所有模型结论均为候选，只有用户确认、确定性工具观测或验证证据可以成为正式状态。

本文所述“PiDeck”指当前已部署的桌面宿主与其 Pi 运行时。方案不会把 Pi 的 project trust 当沙箱，不会声称能从同一可见窗口物理删除历史，也不会在未确认时自动下载、安装、联网、写入、发布、付款或引入外部 Skill/MCP。

## 1.1、方案结论与适用范围

**定位。** 定制目标是把 PiDeck 从“单个通用编码会话”升级为“以用户决定为权威、以结构化状态为工作记忆的本地智能体控制台”。适用对象包括长周期软件开发、研究与方案制作、外部能力评估、需要分阶段执行与可追溯验收的任务；简单问答仍保持默认直通，不强迫进入图谱或多代理流程。

**可实现范围。** Pi 扩展可注册工具与命令、拦截 `input`/`context`/`tool_call`、持久化 `custom` 会话条目、改写压缩、调用桌面 RPC UI；Pi SDK 还可以创建独立 `AgentSession` 或运行时。因此，需求投影、执行账本、受控动作门禁、官员按需审查、会话交接和隔离子代理均可渐进实现。

**不可承诺范围。** 主窗口已发送的历史由 Pi 会话保留；扩展只能在模型请求前过滤或用新会话重建逻辑上下文，不能让 UI 历史物理消失。Pi project trust 只是项目资源加载确认，不是执行隔离；真正不可信代码必须进入容器、VM 或微 VM。任何“全局经验”“能力融合”均不得自动改变路由或安装软件。

## 1.2、现状盘点与约束结论

当前 PiDeck 全局代理目录已有四个基础扩展：`pi-deck-plan-mode.ts` 已实现只读规划、计划确认与进度 widget；`pi-deck-todo.ts` 可将待办状态写入会话分支；`pi-deck-ask-question.ts` 可通过桌面 RPC UI 收集结构化确认；`pi-deck-file-capture.ts` 在写入前保存原文，适合作为变更证据。默认模型为 `gpt-5.6-terra`，同一提供商已有 `luna`、`terra`、`sol` 三条模型路线，并配置了 context-mode MCP。

Pi 运行时允许扩展持久化不进入模型上下文的 `custom` 条目，允许在每次 LLM 调用前通过 `context` 事件投影消息，允许在 `tool_call` 阶段阻断或改写参数，也支持 `/new`、`/fork` 与 SDK 独立会话。现有示例已证明可以用独立 Pi 子进程运行子代理，但该示例默认继承宿主配置，必须增加允许工具、工作区、预算、网络和输出上限，不能直接作为生产调度器。

现状缺口是：尚无项目级权威状态库、执行节点与验收证据映射、统一安全策略、审计日志、来源谱系、独立审查契约和桌面架构视图。方案以新增一个全局 `wuji-legion/` 扩展包补齐；不修改 Pi 核心，不依赖项目内不可信扩展。

# 2、目标架构与权责模型

目标架构将长期事实、短期运行态、模型上下文和审计记录拆开。项目状态库保存版本化需求、用户决定、执行节点与验收映射；Pi JSONL 继续保存原始对话和会话分支；扩展只在调用前取与当前单元有关的最小投影；独立审查和子代理只返回带证据的回执。任何跨层写入必须经过确定性校验、ACL、脱敏、幂等键与追加式审计，模型不能直接把推断写成正式事实。

## 2.1、PiDeck 角色映射

| 无极军团职责 | PiDeck 定制实现 | 正式写权 | 默认模型/运行方式 |
|---|---|---|---|
| 用户 | 桌面聊天、确认弹窗、计划执行选择 | 需求、方案、风险取舍 | 人工 |
| Luna 阿极 | `legion-core` 会话协调器与需求工具 | 需求当前投影；实际由状态服务提交 | `gpt-5.6-luna`，主会话 |
| Sol 参谋本部 | `legion-execution` 规划/调度扩展 | 执行图和证据复核状态；实际由状态服务提交 | `gpt-5.6-sol`，任务级常驻隔离会话 |
| Luna/Terra/Sol 执行节点 | `legion-subagent` 任务工作者 | 仅任务契约授权的制品写权，并交付回执 | 按任务一次选定模型，隔离会话 |
| 官员 | 只读 `review-session`、审查工具与模板 | 无；只产生建议和证据 | 默认 0 个，按契约启动 |
| 保卫科 | `legion-gate` 确定性策略引擎 | 安全事件、处置回执 | 无模型门禁优先；必要时独立审查 |
| 进化主帅 | `legion-lineage` 来源/融合治理 | 能力谱系与发布状态 | 离线判定、用户确认后变更 |

阿极与参谋本部不是两个竞争路由器。前者只决定对话中哪一个需求单元正在被澄清，后者只对已确认快照拆解执行节点。各角色提出变更意图；`legion-store` 是唯一直接写入者。

## 2.2、PiDeck 专属总体架构

```text
PiDeck Desktop（会话、RPC UI、模型选择、文件 Diff）
  └─ 全局 wuji-legion 扩展包
      ├─ legion-core：当前单元、需求快照、上下文投影、会话交接
      ├─ legion-store：SQLite 状态库、迁移、修订、ACL、脱敏、审计
      ├─ legion-execution：执行 DAG、预算、验收映射、熔断与回执
      ├─ legion-gate：命令/文件/网络/密钥/发布的确定性门禁
      ├─ legion-review：官员触发契约、隔离审查、建议记录
      ├─ legion-lineage：来源、资产、融合物种、发布和可达性验证
      └─ legion-subagent：受配额的 Pi SDK/子进程隔离工作会话
          ├─ 每项目 .pi/wuji/legion.db（权威结构化状态）
          ├─ 每项目 .pi/wuji/artifacts/（内容寻址产物与证据）
          └─ 全局 ~/.omp/agent/wuji/（经验、谱系、策略、审计分区）
```

推荐 TypeScript + Node 20 + SQLite（`better-sqlite3`）实现状态层。SQLite 使用 WAL、外键、事务与 `revision` 乐观锁；产物存为 SHA-256 内容 ID 的文件，数据库只存元数据和句柄。这样可在 Windows 离线运行，不引入图数据库、后台守护进程或必需网络服务。

## 2.3、事实、状态与审计的存储边界

**权威事实。** `requirement_unit` 只保存用户目标、要/不要、约束、验收与未决项；`decision_event` 只保存用户采纳、拒绝、暂缓的不可变事件；需求当前态由决策事件投影而成，避免双重权威。`execution_node` 引用精确的需求修订，不得反向改写需求。`acceptance_link` 保存需求—任务—产物—验证的对账链。

**冷证据与运行态。** Pi JSONL 是原始聊天证据；不重复复制全文。代码、网页、日志和大产物只保存脱敏后的内容句柄、范围、采集时间和哈希。会话 custom entry 仅保存 UI 进度与当前指针，断线后从 SQLite 重建。模型推断、官员意见、外部 README、未验证根因都以 `candidate` 保存，不能作为正式事实。

**全局边界。** 全局经验和能力谱系按用户身份/项目命名空间分区；跨项目默认拒绝。读取必须声明目的、最大跳数、最大对象数、字节和时间预算。谱系索引只提供对象定位、当前修订和 ACL 提示，不保存业务正文，且每次解析仍检查 ACL。

# 3、2.1 优先实现方案

2.1 的交付边界是：在不修改 Pi 核心和不依赖后台服务的前提下，建立每项目可恢复的权威状态、计划执行边界、动作前安全门禁、按需审查与能力来源留档。所有新增能力先以全局扩展运行，待测试成熟后再打包为带版本锁定的 Pi package。

## 3.1、需求与决策状态服务

新增 `legion_state` 工具组：`locate_requirement`、`propose_requirement_revision`、`record_user_decision`、`build_requirement_snapshot`、`get_projection`。模型只能先提出结构化变更草案；涉及目标、范围、验收、风险取舍或官员建议时，扩展必须通过现有 `ask_question` 弹出确认，随后由 `legion-store` 在单个事务内追加 `decision_event`、写入新 `requirement_revision`、更新当前投影并记录审计事件。

每个单元使用不可枚举 UUIDv7 `unit_id` 和 `revision_id`，包含状态、证据等级、来源 JSONL entry ID、有效期、分类、父子/依赖关系与内容哈希。首次只实现项目需求图、决策图和对话证据索引，不建设自动语义记忆。`/legion status` 展示当前项目、活跃单元、未决问题、已确认快照和风险；`/legion snapshot` 创建可供执行使用的只读快照。

`context` 事件不再按最近消息数保留内容，而是注入“动态骨架 + 当前单元 + 必要依赖 + 未提交片段 + 当前消息”。已提交聊天在主会话仍可见，但不作为默认模型上下文。摘要不足时由工具按 source entry ID 读取局部 JSONL，而不是扫描全会话。

## 3.2、执行计划、验收证据与熔断账本

`legion_execution` 接收已确认的需求快照，生成带依赖的 `execution_node` DAG。节点固定引用需求修订、输入句柄、允许读取范围、预期产物、验证方法、预算、策略 ID 与单一写入范围。计划模式继续承担用户可见的“先分析、后确认”，但其 Todo 不再是唯一状态；批准后，计划步骤映射为执行节点，完成标记必须附带产物和验证证据才能变为 `verified`。

每次工具或子代理回执写入 `attempt_ledger`：节点、规范化输入、工具/命令、环境、策略、错误指纹、产物哈希、进展证据和时间。完全相同尝试仅在瞬时错误证据下重试一次；同策略两次失败必须变策略；三种策略或五次无进展即熔断并转为 `blocked`。`[DONE:n]` 只更新 UI 进度，不能绕开验收。最终 `/legion accept` 根据 `需求修订→节点→产物→验证→证据` 对账，显示通过、缺口、风险与用户可选动作。

## 3.3、事件式安全门禁与权限确认

新增 `legion-gate`，统一订阅 `tool_call`、`user_bash`、项目 trust 和能力引入入口。门禁按动作而非关键词轮询：命令执行、`edit/write`、网络访问、下载/安装、外部代码/Skill/MCP 引入、密钥/账号、权限提升、Git push、发布、付款和删除都在实际动作前判定。策略输出 `allow`、`confirm`、`block` 或 `sandbox-required`，并写入最小化安全回执。

默认规则是：只读本地操作允许；对项目工作区的普通文件写入由计划批准范围放行；`.env`、凭据目录、Pi 配置、全局扩展、注册表发布、系统目录、删除和网络外传必须二次确认；无 UI 的 RPC/print 模式对确认类动作默认阻断。命令解析采用 allowlist/结构化规则与路径规范化，不能只靠正则；现有 Plan Mode 的只读命令判定可抽取为基础策略，但不得把 `curl`、`wget` 视为默认安全。

密钥检测发生在入库、工具参数、命令输出和产物写入之前；命中后替换为 vault 引用、阻止写入会话扩展状态，并提示轮换。Pi 原生没有沙箱，`sandbox-required` 必须调用 Gondolin、容器或 Windows Sandbox 配置；没有隔离后端时拒绝执行。

## 3.4、按需官员审查机制

`legion-review` 为白帽、质检、审计、合规、根因、性能和保卫科定义触发契约。契约输入为任务类型、执行阶段、产物类别、风险标签、证据缺口、错误重复与性能回退；命中后先添加“应检查项”到当前提示，只有用户要求独立意见、硬风险无法确定性判断或契约阈值满足时，才创建一个隔离 `review-session`。

审查会话只读取快照、相关节点、产物句柄和许可的证据，首轮不读取其他官员结果；返回 `advisory_id`、职权、主张、证据、因果线、置信度、范围、建议与过期时间。阿极通过桌面 UI 将每项标记为采纳、拒绝、暂缓或修改后采纳；只有采纳才产生决策事件和需求修订。白帽只在方案讨论期参与，用户确认进入执行后冷存档。官员不可互相调度、不可发起子代理、不可自行重开审查。

## 3.5、能力谱系与资产可达性管理

`legion-lineage` 提供 `assess_source`、`propose_fusion`、`verify_asset_reachability`、`release_species` 四个受控动作。每个来源按 `source_id + source_version_id` 建档，结论只能是融合提案、仅借鉴、拒绝或待证。未采用来源只保留版本、时间、理由、少量证据句柄与再评估条件；不得复制完整项目、脚本或模板到全局库存。

被采用的原子规则、脚本、模板、组件、配置和示例必须标注 `atom_revision_id`、许可证、依赖、兼容范围和统一入口。融合产物使用 `fusion_species_id / fusion_revision_id / release_id`，记录新增组合能力及父代贡献。批量可达性验证由确定性检查完成：资产 ID 可解析、入口存在、依赖齐全、配置匹配、兼容关系成立，且统一调用器可在受控试运行中加载、渲染或执行。没有调用链的资产不计入融合成果。

默认不扫描上游更新；用户重新提交同一来源版本时直接返回旧判定，提交新版本或显式检查时才做差异分析，并以旧融合物种为父代提出新修订，绝不覆盖旧发布。安装、注册 MCP 或改全局配置仍由保卫科门禁和用户确认控制。

# 4、PiDeck 宿主与桌面端改造

PiDeck 宿主改造不应 fork Pi 内核。扩展先通过 `context`、`before_agent_start`、`session_before_compact` 和会话替换 API 实现逻辑上下文重建；桌面端再消费扩展的状态快照和审计回执展示控制台。需要多模型或真正独立观点时，使用 SDK `AgentSession` 或受配额的 `pi --mode json --no-session` 子进程，而不是在主模型提示中假装分身。

## 4.1、最小上下文投影与同窗逻辑新会话

当需求单元完成确认、任务进入执行、用户切换到另一目标或上下文预算达到阈值时，`legion-core` 创建 `projection_id`。投影包含动态骨架、活跃需求单元、必要依赖、批准决策、相关执行节点、证据句柄、允许工具和字节预算；它不是聊天摘要的替代品。每次 `context` 事件按投影过滤主会话的旧消息，并注入可追溯的投影消息；原始 JSONL 仅供按 entry ID 局部回读。

对于执行、审查和复杂根因任务，桌面端提供“在新工作会话打开”动作：调用 `ctx.newSession()` 或 SDK 创建新会话，以 `parentSession` 保留谱系，并把已审阅的投影作为首条上下文。完成后只回传结构化回执至原会话和 SQLite。此方法在不删除可见历史的前提下给执行分支真正的新上下文；用户可通过会话树审计与回退。默认不自动切换主会话，避免对话中断。

## 4.2、桌面端控制台、交互与可视化

建议在 PiDeck Desktop 新增“无极军团”侧栏/抽屉，并通过现有 RPC Extension UI Protocol 接收 `legion-status`、`legion-confirmation`、`legion-audit` 三类事件。首版分为五个页签：**意图**展示当前需求单元、约束、未决问题和来源；**执行**展示 DAG、节点状态、预算、尝试与熔断；**验收**展示需求—产物—证据矩阵；**风险**展示待确认门禁和官员建议；**谱系**展示来源版本、物种、发布与资产可达性。

所有确认采用结构化弹窗而非让模型用自然语言追问：写入/执行计划、危险操作、接受官员建议、采用融合发布分别显示影响对象、证据、风险、可逆性和可选项。现有 `ask_question` 可立即承担该确认通道；桌面端后续补充批量批准、差异预览、证据跳转、失败熔断复位和导出审计包。`todo` 与 Plan Mode widget 保留，但显示的进度应来自执行账本的只读投影，避免双源状态。

## 4.3、隔离子代理与模型分工

隔离工作者采用两档实现。第一档为 2.1：复用 Pi 的子代理模式，但强制 `--no-session`、显式模型、工具 allowlist、受控 cwd、任务投影文件、总输出上限、超时和并发上限；Luna 执行机械提取/验证，Terra 完成普通实现，Sol 处理架构、复杂推理和高风险根因。子代理不读取主会话 JSONL，不加载项目级 agent/extension，不能修改需求状态或宣布项目完成。

第二档为 3.0：在 PiDeck 主进程使用 SDK 创建 `AgentSession`，注入只读的结构化工具与每任务临时凭据；写入必须经主进程 `legion-store` 和 `legion-gate`。每个 worker 返回 `artifact_handles`、`evidence_handles`、假设、失败、尝试指纹、测量和推荐后续动作。并行任务仅允许读取共享输入；同一写入对象分配唯一租约。全局限制建议从每任务 1 个 worker、每轮最多 2 个并发开始，待审计和预算验证完成后再扩大。

# 5、数据、接口与安全规范

本章将状态库、扩展接口与安全控制固定为可测试契约。实现时不得让桌面 UI、模型提示、Pi 会话 JSONL 或 SQLite 任一方成为未经审计的第二权威；所有写入和副作用都应能从审计事件反查发起人、授权、输入版本、结果和证据句柄。

## 5.1、持久化目录、核心实体与修订事务

每个项目建立 `.pi/wuji/`：`legion.db`、`artifacts/<sha256>`、`audit/`、`exports/`；全局目录只放跨项目经验、能力谱系、策略和不含秘密的汇总审计。核心表为 `requirement_unit/revision`、`decision_event`、`execution_node/dependency`、`attempt_ledger`、`artifact`、`verification`、`advisory`、`security_event`、`source/version/atom`、`fusion_species/revision/release`、`acl`、`audit_event`。所有表都有稳定 ID、`authority`、`status`、`classification`、有效期、证据句柄、`record_hash`、创建/更新者和 `revision`。

写入 API 采用命令事务：验证 schema → 检查项目/对象 ACL → 脱敏 → 校验当前 revision 与幂等键 → 追加审计 → 写新修订或状态迁移 → 更新投影。发生冲突只返回版本差异并要求重新读取/确认，禁止静默覆盖。数据库每日备份到项目受控目录，恢复流程必须校验 schema、审计链和产物哈希；可重建代码索引、临时审查图和研究缓存不进入备份承诺。

## 5.2、扩展工具、命令与事件接口

首版扩展命名统一为 `legion_*`，避免覆盖现有 `todo`、`ask_question` 等 PiDeck 工具。建议工具为：`legion_state`（查询/提案/快照）、`legion_execute`（创建节点/回执/验证）、`legion_review`（请求/返回/采纳建议）、`legion_lineage`（来源判定/发布）、`legion_evidence`（登记/局部读取）和 `legion_status`。所有工具参数携带 `project_id`、`request_id`、目标 ID、预期 revision 与操作理由；响应总是返回 `status`、新 revision、证据句柄、审计 ID 和下一步需要的用户决定。

命令包括 `/legion`、`/legion status`、`/legion snapshot`、`/legion execute`、`/legion review`、`/legion accept`、`/legion audit`、`/legion handoff`。扩展事件职责固定：`input` 绑定当前单元；`before_agent_start` 注入角色/投影；`context` 实施字节受限过滤；`tool_call` 实施安全和预算门禁；`tool_result` 捕获产物与回执；`turn_end` 更新尝试账本；`session_start/session_tree` 重建状态；`session_before_compact` 生成带 ID 的图谱摘要；`session_shutdown` 关闭数据库与子进程。

## 5.3、秘密、隐私、外部内容与审计控制

外部网页、README、MCP 描述、仓库文件和工具输出全部是不可信输入：只能登记为带范围/时间的声明，绝不能驱动安装、配置、联网或写入。网络策略采用域名 allowlist、请求方法、下载尺寸、重定向次数、出站数据分类和任务授权联合判定；检索结果与下载内容在隔离目录保存，未经用户批准不可进入运行能力。

秘密永不进入需求图、执行图、经验图、能力图、普通日志、产物、桌面 widget 或模型投影。检测器将疑似令牌替换为随机 vault reference；审计记录只保存秘密类型、作用域、轮换状态与事件 ID。当前配置中已经发现明文模型提供商凭据，必须在第一阶段开始前立刻撤销/轮换，并迁移到 Pi 支持的认证存储、受保护环境变量或 OS 凭据库；同时检查历史会话、日志、备份和导出物，完成可控副本清理。不要以“文件加密”替代轮换。

审计日志追加式保存读取投影、状态写入、授权变更、门禁决策、子代理启动/停止、失效、删除和导出。哈希只校验内容完整性，不替代审计。按敏感级别配置保留期；删除请求和合规义务优先于“原始证据永久不可变”的假设。

# 6、实施计划与验收

上线顺序坚持“状态与门禁先于智能化”。任何阶段若不能证明写入来源、验收证据、预算和用户确认边界，就不进入下一阶段。生产默认维持单主会话、零真实官员、零后台扫描；多代理与跨项目经验仅以显式功能开关逐步开放。

## 6.1、分阶段路线与交付物

| 阶段 | 目标与交付物 | 上线条件 |
|---|---|---|
| P0：安全基线 | 轮换已暴露凭据；关闭不必要遥测；建立备份、策略测试与项目 trust 规范 | 不再有明文秘密进入配置/日志/状态库 |
| P1：状态核心 | `legion-store/core`、SQLite 迁移、需求/决策/快照、审计、`/legion status` | 用户确认可产生可回溯修订；上下文投影可重建 |
| P2：受控执行 | 执行 DAG、计划映射、证据、尝试账本、熔断、`legion-gate` | 写入和危险动作在副作用前按策略阻断/确认 |
| P3：验收与桌面 | 对账矩阵、控制台页签、确认卡、导出审计包 | 可展示每个已交付需求的验证证据 |
| P4：审查与谱系 | 官员契约、隔离审查回执、来源判定、资产可达性 | 官员建议不自动写入；融合资产可实际调用 |
| P5：3.0 受控扩展 | SDK worker、隔离后端、全局经验候选检索、性能证据 | 预算、ACL、熔断、回收和回归测试稳定 |

每阶段以独立 feature flag 发布，并提供数据库迁移回滚和扩展停用路径；P0—P2 未稳定前禁止并行子代理和自动引入外部能力。

## 6.2、行为验收、测试策略与上线门槛

P1—P3 必须自动化测试以下行为：连续数十轮讨论后切换单元，模型投影不含无关已提交聊天但可沿 ID 回读来源；用户修改一个已确认需求时，仅精确引用该修订的执行节点及下游失效；子代理只收到节点投影，不能写需求或宣告全局完成；计划 `[DONE]` 没有验证证据时不能通过验收。

安全回归必须覆盖：未确认文件写入、删除、安装、网络外传、权限提升、发布、付款、项目扩展加载和敏感路径写入均在动作前被阻断或要求确认；无 UI 模式默认拒绝确认类动作；提示注入文本不能改变策略；密钥样本不进入 SQLite、custom entry、导出和审计正文。熔断测试必须验证相同尝试、同策略失败和任务级无进展分别按阈值停止。

P4—P5 还要进行集成与混沌测试：官员首轮互不可见，未采纳建议不会影响正式状态；来源相同版本去重、新版本只影响相关谱系；资产入口不存在即不能发布；并发 worker 争夺同一写入租约时只有一个成功；崩溃恢复后审计链、修订、产物哈希与预算状态一致。上线门槛是上述用例全绿、数据库迁移可回滚、P0 凭据整改完成、且至少一个真实项目完成端到端验收演练。

## 6.3、明确不做事项、风险与决策点

**明确不做。** 不 fork Pi 内核；不建设自动吸收所有文件/聊天/网页的总图；不在后台扫描来源更新；不默认常驻官员或自动拉起委员会；不自动安装 Skill、MCP、依赖或替换模型路线；不让全球经验自动改任务路由；不把 Pi JSONL 改造成第二权威数据库；不承诺从可见主窗口删除历史；不将 project trust 描述为沙箱。

**主要风险。** 最大技术风险不是图谱建模，而是扩展间工具覆盖、模型绕过自然语言规则、Windows 路径与子进程继承、会话分支状态错配以及明文凭据扩散。因此核心扩展应使用唯一名称、显式加载顺序、事务化状态服务、无 UI 默认拒绝、子进程最小环境变量和端到端回归套件。所有全局配置改变必须经过门禁；Pi package 仅从固定版本的受审计来源安装。

**待用户确认的产品决策。** 第一版应先确定三项默认值：项目状态目录是否随仓库提交（建议默认不提交，仅导出可审计快照）；高风险任务是否强制容器/微 VM（建议强制）；以及是否允许跨项目经验检索（建议默认关闭，P5 仅以候选、显式授权方式开启）。在这三项确认前，按 P0→P2 实施即可形成可用且安全边界清楚的 PiDeck 无极军团 2.1。
