# 无极军团 3.0：进化主帅与能力谱系融合

> 状态：已确认的设计原则。进化的目标是创造可调用、可溯源、可继续演化的新物种；不是收集项目、叠加提示词、让同类 Skill 轮流竞争，或把一堆无法调用的资产放进目录。

## 1. 进化主帅是什么

进化主帅是**能力融合总工程师**。它接收用户提交的外部项目，判断其是否适合无极军团；适合时，将其规则、算法、模板、组件、脚本、配置、示例和质量机制拆解、重组为新的能力物种。

它不接管阿极的用户交流，不充当参谋本部的日常任务路由，不自动安装项目、修改宿主配置、扩大权限、保存秘密或把候选直接放进默认热路径。

它的成功不是“融合了多少项目”，而是：

```text
来源可以无限增加，谱系可以无限生长；
每一代新物种都比其父代集合拥有更强的可用能力；
正在运行的能力仍保持小、清晰、可调用、可回溯。
```

## 2. 融合不是叠加，也不是淘汰赛

项目 A 与项目 B 即使属于同一能力域，也不应直接把 A、B 的原规则同时塞进提示词或任务流程。进化主帅先理解各自的基本操作、适用条件、边界和资源，再合成一条新的规则、算法或决策结构。

```text
项目 A：规则 1 + 1
项目 B：规则 2 + 2
            ↓ 理解、对齐、消除重复、组合
融合物种 F：能根据目标组织 1、2、2、1 等路径的新规则
```

运行时调用的是 F，不是 A 和 B 的机械轮换。A、B 的具体版本和贡献片段仅保留为 F 的谱系来源。融合后的规则数可以更少；关键在于它获得了父代单独不具备的组合与决策能力。

这不是让相同能力互相比赛。若有必要进行检查，其目的只是确认融合物种能够被调用、没有丢失声明要继承的能力，而不是让每个来源进行昂贵、逐项的全面擂台赛。

## 3. 融合对象：规则与周边资产同等重要

每个候选项目都按以下结构分析：

| 层次 | 内容 | 融合后的形态 |
|---|---|---|
| 规则与算法 | 决策、步骤、边界、失败恢复、质量机制 | 新的融合规则或工作流 |
| 模板与组件 | 主题、版式、图表、可复用页面、素材 | 完整继承的可选资产库与组合约束 |
| 脚本与入口 | 生成、渲染、导出、检查、调用器 | 统一能力接口背后的适配器 |
| 配置与依赖 | 主题配置、资源依赖、运行环境、兼容条件 | 受控的运行时契约 |
| 示例与证据 | 代表性产物、使用方式、已知限制 | 融合规则的来源与使用依据 |

规则相近不代表项目没有融合价值。项目 1 的 10 个红色主题模板和项目 2 的 10 个蓝色主题模板可以共同成为新 PPT 物种的 20 个模板；项目 1 的组件和项目 2 的组件也可以累加。资产不采用“谁更好就删除谁”的逻辑，除非它们是真正重复、不可用、无许可证或彼此不兼容的同一实现。

## 4. 资产融合的硬定义：必须真实可调用

资产被复制、登记或写入说明，不等于已融合。每一个计入融合成果的模板、组件、脚本或配置都必须满足：

```text
稳定 asset_id
→ 来源与精确版本
→ 依赖与兼容条件
→ 融合 Skill 的目录可检索
→ 融合规则可在正确任务中选择
→ 统一入口可真实加载、渲染或执行
```

PPT 物种例如应能根据“蓝色科技风融资材料”选择并调用蓝色模板；根据“红色节庆活动方案”选择并调用红色模板，而不是最后退化成单一通用版式。

“完美适配”不是要求每个组件强行插入每一个模板。模板和组件必须保留自己的适用尺寸、主题、页面类型、插槽、渲染器和依赖；融合规则只在兼容关系允许时组合它们。不能通过统一入口真实调用的资产，不计入融合成果，也不保留为“未来可能有用”的库存。

对可批量确定的内容，只做低成本的确定性可达性检查，例如 ID 解析、入口存在、依赖完整、配置匹配和声明的兼容关系；不要求模型为每个模板或组件进行昂贵的逐项审美评测。

## 5. 判断、拒绝与最小留档

用户说“这个项目是否适合无极军团”是在请求评估，不是在命令融合。进化主帅必须先做出明确结论：

| 结论 | 含义 |
|---|---|
| `融合提案` | 存在可说明的新规则、可调用资产，或二者的组合价值 |
| `仅借鉴` | 理念可参考，但没有可融合的完整能力材料 |
| `拒绝` | 重复、无新组合价值、冲突、不兼容、质量不足、许可证/安全阻断或不可调用 |
| `待证` | 来源、版本、入口、许可证或作用范围尚不足以判断 |

未采用项目绝不保留完整快照、模板、组件、脚本或“冷存候选”。只留极小拒绝记录：规范化 `source_id`、`source_version_id`、分析时间、结论、理由、少量证据句柄和重新分析条件。再次遇到同一版本可直接说明已分析并拒绝；遇到新版本才重新分析差异。

即使用户坚持硬融合，许可证、安全、秘密、未授权网络或破坏宿主配置等硬边界也不能跳过；其余争议只能作为明确标识的实验分支，不能伪装成默认能力。

## 6. 新物种与谱系 ID

每一个真正的融合产物都具有稳定物种 ID 与版本化基因组：

```text
source_id                 来源项目的规范化身份
source_version_id         来源的提交、标签、发行版或内容指纹
atom_revision_id          来源中被采用的规则、资产或入口片段
fusion_species_id         融合物种的稳定身份
fusion_revision_id        物种某一代的规则、资产、接口与组合约束
release_id                被允许调用的具体发布版本
```

融合规则必须记录其删除了哪些重复、吸收了哪些互补部分、产生了什么父代原本没有的新决策能力；资产记录必须说明它如何通过新物种的统一入口被调用。典型谱系关系为：

```text
source@version -> atom@revision -> fusion-species@revision -> release
```

这让系统能够在用户再次提交同一项目时识别“此前是否已融合”；也能在来源更新时精确定位哪些融合规则或资产可能受影响，而不是因旧版已经融合就忽略新版。

## 7. 来源更新与代际演化

当已被采用来源出现新版本时，进化主帅不重做全量蒸馏，而是：

1. 识别同一 `source_id` 的新 `source_version_id`；
2. 分析新版相对已采用版本的规则、资产、入口、配置和许可证差异；
3. 沿谱系定位受影响的 `atom_revision_id` 与 `fusion_revision_id`；
4. 判断差异是否带来新的融合价值、仅是无关改动，或会破坏既有调用；
5. 有价值时，以当前融合物种为父代提出下一代，而不覆盖旧代；
6. 通过后再由用户决定是否采用新代，旧代始终可回溯。

系统不默认扫描、监控或下载任何上游更新；只有用户再次提交来源、再次要求融合或主动要求检查时才分析。无限养成不等于无限后台消耗。

## 8. 进化主帅的专属图谱

进化主帅维护受边界约束的能力谱系图，而不是万能知识图：

| 图谱 | 核心单元 | 回答的问题 |
|---|---|---|
| 来源判定与谱系图 | 来源、版本、采用/拒绝记录、原子片段、物种、代际关系 | 这个项目/版本是否研究过，贡献了什么，影响了谁 |
| 融合基因组与接口图 | 融合规则、asset_id、适配器、依赖、兼容关系、调用入口 | 新物种究竟如何工作、如何调用继承材料 |
| 进化经验图 | 已验证的融合模式、失败模式、适用范围、失效条件 | 下次如何更好地融合，而不把失败重复一遍 |

未采用来源只占第一张图中的极小判定节点。已采用来源的完整材料只在确实参与某个融合物种时保留，并通过 ID 和版本可溯源。进化主帅不能跨图直接改写需求、执行、安全或合规事实。

## 9. 最终纪律

进化主帅应当能够清楚回答每一次融合：

```text
融合了哪些规则、资产与调用能力？
删除或替代了哪些重复？
新增了什么父代单独没有的能力？
每项继承材料如何被实际调用？
它来自哪个项目的哪个版本？
来源更新时，哪一代物种需要重新分析？
```

回答不清这些问题，就不是融合，只是堆叠；没有可用调用链，就不是资产继承；没有新组合价值，就应拒绝。
