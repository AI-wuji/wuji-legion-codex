# W5/W6 专家与专家团模板映射

本文件是无极军团专家目录的冷态模板依据。它不是一段泛化的人设，而是把用户提供的 W5/W6 原文素材映射到专家契约和专家团 SOP；目前仅有单专家 worker 可以在预算内编译，团队阶段尚不等于宿主已执行。

课程结构与已经存在的专家、领域主 Skill、规则及可调用资产属于**同一融合谱系**。新增与进化先执行 [统一准入](evolution-admission.md)，核对当前能力的真实入口和行为，再吸收适配片段；55 个共享入口的逐项取舍见 [来源决议账](source-decisions.json)，入口审查的证据边界见 [审查记录](shared-skill-audit-2026-09-27.md)。

来源：

- 用户粘贴的《W6 课程笔记：W5 & W6 提示词素材库》。
- 课程中的 W5 元指令五要素：角色、任务、流程、约束、输出。
- 课程中的 W6 商单四步法：拆需求、规划与报价、搭建专家、打包专家团。
- 用户提供的 `D:\下载\skill共享`，只作为冷态 Skill 来源；运行时不依赖该绝对路径。

## 统一专家模板

每个专家必须同时具备以下内容：

| W5/W6 要素 | manifest 字段 | 执行含义 |
| --- | --- | --- |
| 角色 | `role_type`、`commander`、`mission` | 说明专家是谁、归哪个师团主帅、对什么结果负责 |
| 任务 | `mission`、`prompt_compiler` | 把自然语言需求编译成一个有边界的专业任务 |
| 流程 | `workflow` | 只列当前专家真正需要执行的步骤，不把其他角色的工作塞进来 |
| 约束 | `constraints`、`boundaries`、`anti_triggers` | 不编造、不越权、不把中间物冒充成最终交付 |
| 输入 | `inputs` | 明确缺什么就停在哪一步，不靠猜测补齐 |
| 输出 | `outputs` | 写清交付物、格式、字段和可复用模板变量 |
| 验收 | `acceptance`、`verify` | 定义“做完”的证据，而不是一句“已完成” |
| 白帽/PonyTail | `white_hat_checks`、`ponytail_rules` | 最小正确路径，同时保留必要的事实、安全、授权和验证检查 |
| 进化 | `promotion_evidence` | 只有真实复用、失败、来源和验证证据才能升级 |
| 来源 | `skill_sources`、`source_ids`、`template_basis` | 记录借鉴来源；冷来源不等于已经接通 |

## W6 素材到专家团

W6 3.1–3.6 的四步法不是四个重复角色，而是每个可交付专家团都要拥有的组装流程：

1. **拆需求**：真实目标、交付物、验收标准、风险点。
2. **规划与报价**：试点期、优化期、批量期；周期、里程碑、工具链、质量节点、付款节点和包含/不包含项。
3. **创建专家**：把稳定的子流程固化成 W5 五要素专家契约。
4. **打包专家团**：明确团长/主理人、职责边界、工具链、Skill、并行组、串行依赖、汇编和最终验收。

内容制作团直接复用已有 `requirement-decomposition` 和 `client-proposal` 两位专家（不再造一层“专家团”）：商单路径 `commercial-decompose → commercial-quote` 串行，后者必须等待四问结果；普通内容任务不经过商单路径。专家团配置的 `team_prompt`、`stages`、`parallel_policy` 和 `template_sources` 是四步法的**待执行摘要**；当前路由不会自动把这份阶段表转成全部子代理及阶段回执。完整模板留在本冷目录，避免污染热契约。

W6 3.7“克隆公版专家”只借鉴角色定义、流程、输出、约束和 Skill 的填写法，不能声称本项目已自动克隆；3.8“不建团接力”可由阿极按需拆任务，但当前没有自动将 `@专家A → @专家B → @专家C` 编译为可回执的宿主 DAG。3.9 的八角色工作室逐角色 SOP 见 `ai-video-studio-team.md`；3.10 的“从剧本到成片”要等生成、剪辑和播放回执，不能用阶段表代替。3.11 的 LOGO、网站页、分镜工具和报价工具分别属于媒体、体验、代码/内容任务示例，按需路由，不为每个例子新建固定主帅。3.12 的通用建团模板进入主帅的成员、团长、SOP 和红线配置；不是宿主已创建的专家团实例。W6 4.1 的安装示例只记冷候选，未安装；4.4–4.9 的飞书、Seedance、桌面操作和多 Agent 示例按对应能力、权限与真实宿主回执验收，不默认调用外部服务或修改桌面。

## W6.2 Skill 素材到专家能力

W6.2 里的 Skill 不是再造一层“主帅”。它们进入对应专家的冷能力来源，或由 `skill-packager` 在稳定复用后封装；专家团只负责按任务图选择、编排和验收。

| W6.2 素材 | 运行时承接专家 | 处理方式 |
| --- | --- | --- |
| 商单承接与需求诊断 | `requirement-decomposition`、`studio-owner` | 先拆真实目标、交付物、验收和风险 |

| 客户跟进与成交推进 | `studio-owner`、`content-operations` | 生成可发送话术和下一步，不代发、不承诺成交 |
| 交付验收与回款管理 | `delivery-acceptance` | 交付清单、验收证据、回款状态和失败回执 |

## 不应混淆的层级

- 师团主帅就是专家团本体，不再套一层同名专家团。
- 专家团负责拆解、派活、控制依赖、质检和汇编；单个专家只做自己的专业交付。
- 阿极负责与用户沟通和最终说明；小任务/纯聊天不调用参谋部。
- 专家、专家团和阿极都遵守 PonyTail；能直接完成就不搭流程，能一行解决就不写多行。
- Skill 作为专家的冷能力来源，不把全部 Skill 原文塞进每个 worker contract。
