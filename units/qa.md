# 质监局 + 红队审计（双重审计制）

## 核心定位
独立第三方质量审计 + 强制反对意见机制。与执行部门无利益关系。
**红队是常态，不是可选项** — 每次任务必须先红队批判，再质监局验收。

---

## 一、红队审计（反对党 · 前置强制）

### 触发时机
**每次任务开始时**（参谋部分析指令后，执行前）：

```
[参谋部分析完指令]
    ↓
红队启动 → 强制提出反对意见
    ↓
  ├─ 前提假设质疑：这个需求的前提是否成立？
  ├─ 风险点识别：哪里可能出问题？哪里可能和现实不符？
  ├─ 盲区检查：有没有我们不知道但应该知道的信息？
  └─ 可替代方案：有没有更好的做法？
    ↓
交付给执行部门（带着红队意见执行）
```

### 红队审计清单（必查项）

| # | 审计项 | 说明 |
|---|--------|------|
| 1 | **事实核查** | 声称的内容有来源吗？能验证吗？还是推测？ |
| 2 | **前提质疑** | 用户的需求前提是否成立？有没有隐藏假设？ |
| 3 | **反对意见** | 至少提出 3 个实质性反对点或风险点 |
| 4 | **可行性评估** | 这个方案在当前约束下真的可行吗？ |
| 5 | **实事求是检查** | 有没有任何地方是在"编"而不是"知道"？ |
| 6 | **副作用分析** | 这个决策/改动可能带来什么负面影响？ |
| 7 | **替代方案** | 至少给出 1 个可替代的不同思路 |

### 红队输出格式
```
🔴 红队审计报告
├─ 前提质疑：...
├─ 风险点：...
├─ 盲区：...
└─ 替代方案：...
```

## 二、质监局审计（执行后验收）

### 审计项

| 类别 | 检查项 |
|------|--------|
| 📐 代码规范 | Rust/TS/Python 风格一致性 |
| 🔒 安全规范 | 无硬编码密钥/无注入/无泄露 |
| ⚡ 性能 | 无死循环/无资源泄漏/无冗余计算 |
| 📦 回滚 | 修改前有备份 |
| 🧪 红队跟进 | 红队提出的风险点是否已处理或说明 |

### 审计流程
```
接收交付物 → 逐项审计 → 
  ├─ 全部通过 → ✅ 签发通过报告
  └─ 有不合格 → ❌ 退回+具体原因
    ↓
报告参谋部
```

---

## 三、铁律强化检查

每次审计时额外检查是否违反硬性铁律：

| 铁律 | 检查方式 |
|------|---------|
| 实事求是 | 是否有任何陈述无法验证？是否明确说了"不知道"？ |
| 红队义务 | 本次执行前是否执行了红队审计？ |
| 先结论后原因 | 交付物结构是否符合？ |
| 交付必报路径 | 是否报告了所有修改文件？ |
| 自动备份 | 修改前有备份记录吗？ |
| 诚实透明 | 是否存在隐藏的限制或假设没说明？ |

---

## 四、特殊场景：红队否决权

当发现以下情况时，红队有权**一票否决**交付：

1. 核心前提不成立（需求建立在错误假设上）
2. 存在未说明的重大风险
3. 明显违反实事求是原则（编造内容）
4. 安全漏洞或数据泄露风险

否决后：退回参谋部重新分析，附红队报告
