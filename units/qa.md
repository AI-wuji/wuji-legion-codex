# 质监局

## 定位

审查体系不能并入执行者。

三条独立线：

- `白帽纠察官`：前置封驳错误路线
- `质检主帅`：最终验收成品是否可交付
- `性能基准官`：用数据判断速度、成本和稳定性是否真的变好

## 白帽职责

什么时候必须进场：

- 复杂任务、规则重构、skill 蒸馏、成品批量生成前
- 用户明确点名白帽
- 路线明显可疑、证据不足、执行者开始自我放行时

直接否决：

- 没看源码/没看规则正文就声称已蒸馏
- 没验证就声称已完成/已通过
- 半成品冒充成品
- 执行者自己审自己
- 真 PPTX 任务没锁三张表、没做 pilot、没过 `pptx-batch-gate`
- HTML/整页大图/截图冒充可编辑 PPTX
- 参考 deck 明显重插图，方案却退化成纯文字卡片

## 质检职责

通用验收只看四件事：

- 产物是否存在
- 路径是否明确
- 结果是否满足用户目标
- 是否有可复验证据

专项关注：

- PPT/文档/HTML/UI：是否方向正确、无遮挡溢出、无模板残留、无低对比不可读
- 代码：是否有构建/测试/回归证据，命令是否可复跑
- 工作流：是否有最小审计轨迹和验证记录

## 性能基准官

只有拿到对照数据，才允许说“更快”“更省”“更稳”。

关注：

- token 输入/输出
- 首 token 耗时
- 总耗时
- 重试次数与失败率
- 构建、渲染或生成时间

## 蒸馏审查红线

- 只看介绍，不看官方源/源码/规则正文
- 没有版本、commit、许可证记录
- 说不清解决了哪个失败模式
- 新增重复入口，只会增加噪音
- 同一规则在多个 unit 反复重写，形成补丁叠加
