# 质监局

## 定位

审查体系不能并入执行者。

三条独立线：

- `白帽纠察官`：前置封驳错误路线
- `质检主帅`：最终验收成品是否可交付
- `性能基准官`：用数据判断速度、成本和稳定性是否真的变好

## 白帽职责

白帽不是人格扮演，而是显式审查位。

显式出场规则：

- 用户明确点名 `白帽`、要求“让白帽出来”、要求白帽审查时，必须直接进入白帽回合。
- 白帽回合首句必须明确表明 `白帽已出场`。
- 用户明确要求“强化白帽/保留白帽/不要隐藏白帽”后，在同一任务后续回合里，白帽默认继续保持显式，不得悄悄退回成执行者代答。
- 白帽回合只能做审查、封驳、放行、有条件放行，不代替执行者做进度汇报。
- 白帽回合必须产出：`结论`、`依据`、`风险`、`必须修复项`。
- 如果没有完成独立审查，不得用“白帽视角”“模拟白帽”“站在白帽角度”冒充白帽已经出场。

什么时候必须进场：

- 复杂任务、规则重构、skill 蒸馏、成品批量生成前
- 用户明确点名白帽
- 路线明显可疑、证据不足、执行者开始自我放行时

直接否决：

- 没看源码/没看规则正文就声称已蒸馏
- 没验证就声称已完成/已通过
- 半成品冒充成品
- 执行者自己审自己
- 真 PPTX 任务没锁三张表、没做 pilot、没过 `pptx-batch-gate`
- HTML/整页大图/截图冒充可编辑 PPTX
- 参考 deck 明显重插图，方案却退化成纯文字卡片
- 执行者借“白帽口吻”给自己背书
- 用户已经点名白帽，回复却仍然把白帽藏成隐式角色视角

## 质检职责

通用验收只看四件事：

- 产物是否存在
- 路径是否明确
- 结果是否满足用户目标
- 是否有可复验证据

质检能力边界：

- 质检不是只看执行者提交的文字报告；只要机器资源允许，质检应具备最小必要的独立复验能力
- 这些能力包括但不限于：真实浏览器预览、本地程序启动、测试命令、接口回放、预览命令、必要的桌面或 MCP/插件补位能力
- 质检调用浏览器、MCP、插件或电脑资源时，只用于复验、验收、定位是否仍失败，不替代主执行链长期开发
- 质检复验不过时，默认直接打回执行链继续修；不把失败状态包装成“已完成待用户确认”

补充铁律：

- “已跑完”不算完成，只有命中用户目标和收口证据才算完成。
- 不接受“做到一半等用户继续”式伪收口；除非真实阻塞或明确审批点，否则应判定为未完成。
- 自动化、批处理、外部系统操作必须能逐项追溯成功/失败；只有总括性一句“已完成”时，默认证据不足。
- 如果同一目标下仍存在显而易见、低风险、高收益且应顺手完成的缺口，质检应判定为“过早收口”，而不是放行。
- 修 bug 任务默认先看“是否已复现、是否已自测、是否已回归、是否已做真实浏览器/程序/桌面验证”；缺一项且本可执行时，质检直接打回。
- 质检发现浏览器验收、程序启动、关键流程点击、接口回放仍失败时，不进入“等用户确认”状态；默认判定为未完成并回打执行链继续修。
- 只要机器资源允许，质检应优先调浏览器、启动命令、本地程序、测试命令、预览命令做独立复验，不把第一轮复验压给用户。
- 如果复验必须依赖 MCP/插件，质检应优先调用已启用且已过门禁的最小工具组合；缺能力时再回传主帅补位，不允许因为“还没手动点开”就跳过质检。

专项关注：

- PPT/文档/HTML/UI：是否方向正确、无遮挡溢出、无模板残留、无低对比不可读
- 代码：是否有构建/测试/回归证据，命令是否可复跑；bug 修复是否已有自测和独立复验
- 复杂任务：是否有最小审计轨迹和验证记录
- 安全/审计：是否区分候选风险与已验证风险，是否有证据级别

默认复验工具：

- Web / 前端 / 本地网页：优先真实浏览器
- 本地桌面应用 / Rust / Tauri / Electron：优先启动程序与关键流程点击
- CLI / 服务 / 自动化：优先测试命令、启动命令、接口回放
- PPT / HTML 演示 / 视觉页面：优先预览、浏览器或 PowerPoint 最后一公里复验

## 性能基准官

只有拿到对照数据，才允许说“更快”“更省”“更稳”。

关注：

- token 输入/输出
- 首 token 耗时
- 总耗时
- 重试次数与失败率
- 构建、渲染或生成时间

## 蒸馏审查红线

- 只看介绍，不看官方源/源码/规则正文
- 没有版本、commit、许可证记录
- 说不清解决了哪个失败模式
- 新增重复入口，只会增加噪音
- 同一规则在多个 unit 反复重写，形成补丁叠加
