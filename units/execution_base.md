# Execution Base Mirror

Mirror source: `kernel-source.json`

## Role

The execution base is layer 3 only:

1. `deterministic-execution`
2. Go `wuji-cli`
3. repeatable local gates and audits

It is not a second router, not a second command system, and not a replacement for owner judgment.

## Main-chain scope

Main-chain execution base duties:

- `guard`
- `audit`
- `bench`
- `context-pack`
- `route-task`
- specialized preflight and batch gates
- `terminal-real-run-verification` evidence capture when a local command, browser, program, export, or artifact check is available
- non-blocking closeout sound via `scripts/beep.ps1` when work is not FAST_REPLY

## Execution Budget

`execution_budget_contract` controls gate cost:

- `LIGHT_TASK` runs targeted verification only and must not repeat a full suite after small edits.
- `STRUCTURAL_TASK` may run targeted gates during work and at most one full verification at final when the touched surface requires it.
- `RELEASE_TASK` runs full audit once at final.
- `runtime-context-audit` is only for token, cost, cache, backend usage, or outer-context claims.

The execution base must prefer targeted verification before full-suite verification.

## Non-main-chain scope

Allowed as on-demand or offline governance only:

- distillation helpers
- prompt evaluation
- feedback dataset generation
- special pipeline utilities

These may exist, but they do not become resident policy by default.

## Hard boundary

The execution base must not:

- create a parallel routing layer
- silently replace oversight
- claim completion without evidence
- expand stable prefix with large helper doctrine
- treat a non-run plan, explanation, or checklist as real-run proof

## Optimization posture

Execution-base optimization is valid only when it improves the whole system:

- smaller stable prefix
- lower total token cost
- equal or better first-pass hit rate
- equal or better verification strength

If a saving weakens evidence or increases rework, it is a regression.
