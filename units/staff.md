# 参谋本部 — MoE并行评估中枢（常驻·预加载）

## 核心定位
MoE (Mixture of Experts) 架构。输入指令后，**并行派发给多个专家部门评估**，加权汇总后做路由决策。
不再是串行"如果→那么"的决策树，而是多专家并行投票+加权路由。

---

## 一、MoE 并行评估架构

```
                    [用户指令]
                        │
                        ▼
              ┌─────────────────────┐
              │   MoE Gating (门控)  │ ← 输入标准化+拆解
              │   拆分为N个子意图      │
              └────────┬────────────┘
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ Expert 1 │ │ Expert 2 │ │ Expert 3 │  ← 并行评估（Promise.allSettled）
   │ (内容师)  │ │ (视觉师)  │ │ (开发师)  │
   └─────┬────┘ └─────┬────┘ └─────┬────┘
         │            │            │
         └────────────┼────────────┘
                      ▼
              ┌─────────────────────┐
              │  加权汇总 + 路由决策  │ ← 各专家输出打分+置信度
              │  激活对应部门         │ ← 可同时激活多个
              └─────────────────────┘
```

### MoE Gating（门控网络）

输入指令后，门控拆解为N个子意图，每个子意图并行发送给相关的专家评估：

```json
{
  "input": "帮我做个Rust的PPT，再写个短视频脚本",
  "sub_intents": [
    {"task": "PPT设计", "weight": 0.5, "experts": ["visual", "content"]},
    {"task": "短视频脚本", "weight": 0.5, "experts": ["content"]},
    {"task": "Rust技术内容", "weight": 0.3, "experts": ["dev", "content"]}
  ]
}
```

## 二、专家并行评估输出格式

每个被调用的专家部门输出统一格式的评估结果：

```json
{
  "expert": "visual.md",
  "confidence": 0.85,
  "relevance": "高",
  "action": "需要激活visual.md，同时建议激活content.md协同",
  "sub_tasks": [
    "确定PPT风格（企业/学术/创意）",
    "调用臧老师设计引擎",
    "准备Rust技术内容布局"
  ],
  "parallel_safe": true
}
```

### 置信度标准

| 置信度 | 含义 | 行动 |
|--------|------|------|
| 0.8-1.0 | 高度相关 | 必须激活 |
| 0.5-0.8 | 中度相关 | 建议激活 |
| 0.2-0.5 | 低度相关 | 可选激活 |
| 0-0.2 | 不相关 | 不激活 |

## 三、自动激活链（多部门并行激活）

```
[MoE汇总完成]
    ↓
白帽纠察（并行触发）
    ↓
根据汇总结果激活：
  ├─ 单一任务 → 激活主部门（串行执行）
  ├─ 复合任务 → 激活多个部门（并行执行）
  │   ├─ visual.md + content.md → 并行做PPT和文案
  │   ├─ dev.md + comfyui.md → 并行开发和渲染
  │   └─ intel.md + nuwa.md → 并行搜索和调专家
  │
  └─ 复杂项目 → 多部门并行 + 远征军外派辅助
    ↓
各部门按 parallel_safe 标识决定执行方式：
  ├─ parallel_safe: true → 与其他部门并行执行
  └─ parallel_safe: false → 等待依赖部门完成后执行
```

## 四、并行执行协议

### 部门依赖关系表
```
visual.md ← 依赖 content.md 提供 slide-spec.json
comfyui.md ← 依赖 visual.md 提供图片素材
content.md → 不依赖其他部门（独立）
dev.md → 不依赖其他部门（独立）
intel.md → 不依赖其他部门（独立）
security.md → 依赖 intel.md 的一审结果
qa.md → 不依赖其他部门（独立，最后执行）
```

### 并行执行规则
```
无依赖的部门 → 立即并行执行
有依赖的部门 → 等待上游完成后执行
复合流水线 → content → visual → comfyui 保持串行管线
独立任务 → 全并行
```

## 六、执行计划器（MoE核心输出）

MoE门控拆解任务后，不是直接激活部门，而是先生成一个**执行计划**。

### 执行计划格式
```
任务: [任务简述]
计划:
  阶段1: [部门A] → [具体工作] (独立/可并行)
  阶段2: [部门B] + [部门C] → [并行工作] (并行)
  阶段3: [部门D] → [依赖B和C的输出] (串行)
白帽纠察: [质疑点/风险/盲区]
预计交付: [时间估计]
```

### 执行计划示例
```
任务: "做一个Rust项目的介绍PPT"
计划:
  阶段1: dev.md → 整理Rust项目技术要点 (独立)
  阶段2: visual.md + content.md → 设计PPT + 写文案 (并行)
  阶段3: comfyui.md → PPT渲染为视频 (依赖阶段2)
白帽纠察: "PPT受众是谁？技术深度到什么级别？时间要求？"
预计交付: 30分钟
```

### 并行/串行判定规则
| 条件 | 模式 | 说明 |
|------|------|------|
| 两部门无依赖关系 | ⚡ 并行 | 同时启动，各自交付 |
| 一部门输出是另一部门输入 | ➡️ 串行 | 等上游完成后启动 |
| 多个独立子任务 | ⚡ 全并行 | Promise.allSettled |
| 需要决策后才能继续 | ⏸️ 暂停 | 等人类确认 |

## 七、冲突解决协议（多Agent并行时的争议处理）

### 冲突场景
```
场景1: visual.md说"用蓝色主调"，content.md说"用红色"
场景2: dev.md说"用框架A"，security.md说"框架A有漏洞"
场景3: 两个专家对同一问题给出不同答案
```

### 解决规则（优先级从高到低）
| 优先级 | 裁决者 | 适用场景 |
|--------|--------|---------|
| 1. **人类决策** | 用户/项目经理 | 任何争议最终由人类拍板 |
| 2. **安全优先** | security.md | 涉及安全问题时安全局一票否决 |
| 3. **白帽纠察** | qa.md | 争议双方各提交证据，白帽纠察评估 |
| 4. **主专家优先** | 任务的主部门 | 辅助部门的意见可作为参考但不强制 |

### 争议记录格式
```
争议: [双方观点]
裁决者: [谁做的决定]
裁决结果: [最终选择]
理由: [为什么这样选]
```

## 七、省token策略（MoE优化版）

- MoE门控只输出意图拆解和置信度，不输出完整评估报告
- 各部门只加载自己的规则，不加载其他部门的
- 并行执行时共享上下文，不重复传递
- 白帽纠察输出精简版（仅反对点，不重复全量）
