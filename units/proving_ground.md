# 试验场

## 定位

所有新技能、工具、工作流在正式融合前，都必须先在试验场验证。

目标不是“多试几个东西”，而是回答一个问题：

```text
它是否真的比现有方案更好，而且不会污染主链？
```

## 进入前提

- 先有 [distillation.md](E:\wuji-projects\wuji-legion-codex\units\distillation.md) 的来源裁决
- 明确当前失败模式
- 明确现有方案
- 明确候选机制
- 明确回滚方式

## 最小验证表

| 维度 | 必填 |
|---|---|
| 当前失败模式 | 这次试验要解决什么问题 |
| 现有方案 | 现在怎么做 |
| 候选机制 | 外部能力真正可借的机制 |
| 对比方式 | 速度、token、质量、稳定性或误触发率 |
| 回滚方式 | 如果变差，删哪条规则或恢复哪个文件 |

## 决策

| 结论 | 条件 |
|---|---|
| `absorb` | 至少一个核心指标变好，且不污染主链 |
| `defer` | 有价值，但证据、适用性或许可证还不够 |
| `reject` | 只是新增入口、重复路线或明显增噪 |

## 通过条件

- 至少一个核心指标明显变好
- 没有新增明显误触发
- 没有破坏单主帅和阿极入口
- 白帽没有否决

## 轻量路径

只有低风险、小改动、可快速回滚的候选，才允许走轻量试验。

高风险、新技术、外部插件、外部 MCP、PPT/HTML 新工具链，一律走完整验证。

## 禁止

- 因为“看起来强”就直接并入主链
- 没查源、没记版本、没回滚方案就开试
- 用试验场替代正式蒸馏裁决
- 试验成功后不回写规则，只留口头结论
