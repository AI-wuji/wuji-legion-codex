# 试验场 — 沙箱化测试 + 对比评估 + 融合验证

## 核心定位
所有新技能/工具/工作流在正式融合前，必须经过试验场验证。沙箱化运行，不影响在产系统。

---

## 一、试验流程

```
[新技能/工具]
    ↓
① 情报局搜索→安全局二审→参谋部判定可试
    ↓
② 试验场沙箱化运行：
  ├─ 场景1: 真实场景复现
  ├─ 场景2: 压力测试（边界条件）
  └─ 场景3: 与现有方案对比
    ↓
③ 评估报告 → 质监局验收 → 白帽纠察审计
    ↓
④ 通过 → 正式融合 | 不通过 → 记录到进化部
```

---

## 二、评估标准

| 维度 | 评分标准（1-5） |
|------|----------------|
| 功能完整性 | 功能是否按预期工作 |
| 性能表现 | 速度/资源消耗对比 |
| 兼容性 | 与现有系统是否有冲突 |
| 可维护性 | 文档/代码质量 |
| 安全等级 | 安全局评估结果 |

### 对比测试表
```markdown
| 维度 | 现有方案 | 新方案 | 差异 |
|------|---------|--------|------|
| 速度 | X ms | Y ms | +-Z% |
| 质量 | X/5 | Y/5 | +-Z |
| 资源占用 | X MB | Y MB | +-Z% |
| 复杂度 | X/5 | Y/5 | +-Z |
```

---

## 三、融合决策树

```
[评估报告完成]
    ↓
评估总分：
  ├─ ≥4分 → ✅ 直接融合
  ├─ 3-4分 → ⚠️ 有条件融合（记录风险点）
  └─ <3分 → ❌ 拒绝融合（记录原因，进化部复盘）
```

### 融合后跟踪
融合后7天内自动跟踪是否有回归问题，如有问题自动回滚。

## 四、外部能力试验范围

外部 skill/MCP/插件只能在试验场通过后进入正式路由，不允许因为“看起来强”就直接叠加。

| 候选能力 | 试验重点 | 通过条件 |
|----------|----------|----------|
| 新 MCP Server | 工具边界、权限、稳定性、错误恢复 | 能被参谋本部按需调用，且安全局通过 |
| 新 ComfyUI 节点 | 安装脚本、依赖、出图质量、速度 | 比现有链路质量/速度至少一项明显提升 |
| 新 Codex 插件 | OAuth权限、实际可用性、和现有插件重叠度 | 能融入现有部门，不形成重复入口 |
| 新 skill | 与女娲专家库/现有unit的重叠度 | 能增强现有流程，而不是另起一套流程 |
| PPT/HTML工具 | 输出质量、可编辑性、依赖成本、和现有链路重叠度 | 只补短板，不替代主线 |

## 蒸馏候选验证

外部 skill、工作流或工具在正式蒸馏前，必须先有 [distillation.md](distillation.md) 的来源裁决，再进入试验场。

最小验证表：

| 维度 | 必填 |
|---|---|
| 当前失败模式 | 这次蒸馏要解决什么问题 |
| 现有方案 | 当前无极军团怎么做 |
| 候选机制 | 外部来源真正可借鉴的机制 |
| 对比方式 | 速度、token、质量、稳定性或误触发率 |
| 回滚方式 | 如果变差，删哪条规则或恢复哪个文件 |

通过条件：

- 至少一个核心指标变好。
- 没有新增明显误触发。
- 没有破坏单主帅和阿极入口。
- 白帽没有否决。

### PPT/HTML候选最终裁决

| 候选 | 裁决 | 后续处理 |
|------|------|----------|
| PptxGenJS | 保留，按需试验接入 | 只有现有PPT链路不足时才进入沙箱试验 |
| Marp | 保留，轻量草稿链路 | 仅用于Markdown快速出草稿演示 |
| reveal.js | 保留，Web演示专用 | 仅用于网页deck/在线演示，不替代PPTX |
| shadcn/ui | 保留，组件参考 | 不自动安装依赖，只吸收组件设计思想 |
| html2pptx | 丢弃默认接入 | 不进入默认链路，避免布局不稳定污染PPT交付 |
| daisyUI | 丢弃默认接入 | 不进入默认链路，避免模板味和低质组件污染视觉输出 |

原则：保留项必须有触发条件；丢弃项不再占用主路由。用户明确指定时，可以临时重新评估。
